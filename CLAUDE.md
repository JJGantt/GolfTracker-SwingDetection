This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

StrokeSaver is a native SwiftUI golf tracking application for iOS and Apple Watch. The app provides real-time GPS-based distance tracking, stroke recording, and motion detection for swing analysis.

### Naming: product vs. code

The product is **StrokeSaver** — that is the App Store / TestFlight name (app id `6756589450`) and
the name every user-facing string, `CFBundleDisplayName`, and permission prompt must use.
`GolfTracker` / `Golf Tracker` were both taken on the store.

Everything *internal* is still named `GolfTracker` and must stay that way:

| Kind | Value | Change? |
|---|---|---|
| Product / display name | `StrokeSaver` | this is the current name |
| Bundle IDs | `com.Jared.GolfTracker`, `com.Jared.GolfTracker.watchkitapp` | **never** — tied to the ASC record |
| Xcode project / scheme / targets | `GolfTracker.xcodeproj`, `GolfTracker`, `GolfWatch Watch App` | no |
| Source dirs, `GolfTrackerApp`, `GolfTrackerWatchApp` | as-is | no |
| Repo + site | `GolfTracker-SwingDetection`, `jjgantt.github.io/golftracker-site` | no — the site URLs are registered in ASC |

So when a doc or a string says `GolfTracker`, ask which one it means: a path/target/bundle id keeps
the old name, anything a user reads says StrokeSaver.

**Key Technologies:**
- SwiftUI for UI across both platforms
- MapKit for maps
- CoreLocation for GPS tracking
- CoreMotion for swing detection (Watch)
- WatchConnectivity for iPhone-Watch sync
- HealthKit for workout tracking (Watch)

## Doc-Drift Pre-Commit Hook

`.git/hooks/pre-commit` blocks any commit that stages a `.swift` file under `GolfTracker/` or `GolfWatch Watch App/` without also staging an update to `CLAUDE.md`. (The hook lives in `.git/hooks`, so it is per checkout and not versioned.) The intent is to force the docs to move with the code.

**Claude is authorized to bypass this hook via `SKIP_DOC_CHECK=1 git commit ...` when the commit is genuinely cosmetic and cannot cause drift.** This overrides the global "never skip hooks without asking" rule, for this repo only.

**Self-bypass IS allowed for:**
- Comment / docstring changes only
- Whitespace or formatting only
- Log message / string literal changes with no semantic shift
- Local variable / private function renames with no external API change
- Test-file changes that don't alter documented behavior
- Dead-code removal (unused private helpers, unreachable branches)

**Self-bypass is NOT allowed for:**
- Detection-algorithm logic, thresholds, gate values, state machines
- New / changed / removed `@Published` properties or public methods on any `*Manager` or `*DataStore`
- `Models.swift` field or enum changes
- `WatchConnectivityManager` message shapes or new message types
- User-visible UI flow changes (stroke recording, hole navigation, round lifecycle, settings)
- GPS, battery, power-management, or workout-session behavior
- File additions or removals
- Anything a future reader of the docs would be surprised by

When in doubt, **update the doc instead of bypassing**. Bypasses should be rare; if they happen more than occasionally for a given area, that's a signal the docs need a section covering it.

## Architecture

### Two-Target Structure

The project contains two main targets that share data models but have separate UI implementations:

1. `GolfTracker` target (iOS) - Full-featured iPhone app with course management, round history, and detailed shot tracking
2. **GolfWatch Watch App** (watchOS) - Companion app for on-course tracking with motion detection

### Data Synchronization Architecture

The iPhone and Watch apps communicate bidirectionally via **WatchConnectivity**:

- **iPhone → Watch**: Round data (including course and hole information)
- **Watch → iPhone**: Recorded strokes, motion data CSV files, round updates
- **Bidirectional**: Hole navigation sync, target marker sync, hole creation/editing

**Critical Implementation Detail**: Both platforms maintain their own `DataStore` instances backed by SwiftData (`@Model` classes in `Models.swift`):
- iOS: `DataStore` in `GolfTracker/Services/DataStore.swift` (club management in `DataStore+Clubs.swift`, the green detector in `HoleDetectionAnalyzer.swift`)
- watchOS: `WatchDataStore` in `GolfWatch Watch App/Services/WatchDataStore.swift`

What both do the same way is written once, in `RoundStoreShared.swift` (compiled into both targets): starting a round where the user stands (`startRoundAtCurrentLocation` → resolver → course / scorecard / course-name pickers), the green candidates (`filteredGreenCandidates`, via `GreenCandidates`), club lookups, and the round-lifecycle sweep. Each store conforms to `RoundStoreShared` and supplies its state and the few platform hooks (how it ends a round, how it records server activity, whether a start without a fix asks for location permission). Change that behaviour there, not in a store.

Each gets a `ModelContainer` injected at app startup (`configure(container:)`). The singleton stores a **single shared `ModelContext`** for its lifetime (exposed as `.modelContext`) — *not* a fresh `ModelContext(container)` per access. The fresh-per-access pattern produces stale-read bugs (we hit a 21s gap where `addNextHole` mutated `round.currentHoleIndex` and saved, then a fresh-context fetch in the view body kept reading the old value for ~21 seconds; the new hole was visible because inserts propagate via the persistent store SELECT, but the index update wasn't because per-context cache coherence is delayed). `RealtimeSync.context` delegates to the platform DataStore's shared context so postgres-changes echoes apply to the same context view code reads from. Round/Stroke/Course/etc. are `@Model` classes — they're reference types and SwiftData tracks change notifications automatically. **A round owns its holes; a course owns its holes; they are never the same objects.** `Round.holes` mirrors the round's `round_holes` rows and `Course.holes` mirrors the course's `holes` rows, on both devices. A round starts with copies of the course's holes (`Hole.roundCopy`), and a round hole's id is `Hole.roundHoleId(roundId:number:)` — derived from the round and the hole number, so any device that creates or repairs a round's hole N writes the same row. Course edits during a round reach the round in progress through `DataStore.updateActiveRoundHoles`, matched by number; finished rounds keep the holes they were played with. Why it is this way: `Hole.round` is to-one, and rounds used to be handed the course's own `Hole` instances. The phone then crashed on the next round at that course (SwiftData's `This relationship already has a value but it's not the target`), and older rounds' holes drained into newer ones. What's left of that: stores that still share are split at launch (`ModelContext.separateRoundHolesFromCourseHoles`, both platforms), whose `round_holes` rows are rewritten to the copies' ids (`SupabaseSync.rewritePendingRoundHoles`, retried each launch until it lands); `RealtimeSync.applyHole` ignores a row whose id belongs to the other kind of hole, so a leftover row can never re-attach a course's hole to a round; and `Round.holes` cascades, which is only safe because of that launch split. A course holds one hole per number: `applyHole` drops any other local hole with the number a server `holes` row arrives for — except that a shared row never replaces the user's own hole for that number (see Course holes: shared and personal) — and `RealtimeSync.reconcileCourseHoles` re-applies every local course's server rows at launch, which repairs courses the phone doubled and fills in `Hole.ownerId` for holes stored before it existed. The phone doubled them by building a local copy of a course the server already had; `DataStore.courseForRound` now fetches the server's course and holes first (`fetchAndInsertCourse`). **Which hole a round is on is `Round.currentHoleNumber`, a hole number, resolved against the round's own holes (`Round.currentHole`, `hole(after:)`, `hole(before:)`).** It used to be a position in each device's own sorted list, and the same position named different holes whenever the two lists differed. Neither Play screen keeps a hole of its own: the phone's `HolePlayView` reads the round's number, and holds a local `reviewHoleNumber` only when opened on a hole to look at it (from a round's detail), which never writes the round. A hole change writes just `current_hole_number` and `last_activity_at` (`SupabaseSync.updateCurrentHole`, a PATCH); `upsertRound` writes only the round row, and a round's holes are written when created or changed (`upsertRoundHoles`, `upsertRoundHole`). `rounds.current_hole_index` is legacy: a trigger (migration 00051) keeps it and `current_hole_number` naming the same hole whichever one a client writes, so an older build on one device stays in step, and the local `Round.currentHoleIndex` is read only by the one-time launch backfill. (3) **Starting a round on the phone at a course whose holes still point at an earlier round crashes the app.** `Round.init` hands `course.holes` to a round that is not yet in the context, and the insert in `saveRounds` then hits SwiftData's `This relationship already has a value but it's not the target` assertion (`ModelContext.swift:935`, from `DataStore.startRound(for:)`). It needs the earlier round to have been started on the phone too: the watch builds a fresh snapshot of `Hole`s for every round, and so the server's `round_holes` rows carry their own ids per round, so only the phone shares instances. Reproduced 2026-09-14 on a second Palm round.

Round/Stroke sync between phone and watch goes through Supabase (Realtime + DB-as-truth), never a WatchConnectivity message of its own. The server's rows reach a solo watch through the phone: every `rounds`, `round_holes`, `strokes`, `targets` and `holes` row the phone's `RealtimeSync` applies is forwarded with `WatchConnectivityManager.relayRow` (live `sendMessage` when reachable, else `transferUserInfo`, which queues in order) and applied on the watch by `RealtimeSync.applyRelayed` through the same `apply` path. Otherwise WatchConnectivity carries auth session push (iPhone → Watch), hole-detection data push, and motion CSV file transfers.

When modifying data sync, update both the sending logic in `WatchConnectivityManager` and the receiving callbacks in both DataStore implementations.

### State Management Pattern

All major features use `ObservableObject` classes as single sources of truth:
- `DataStore` / `WatchDataStore` - Course and round data. Both are `@MainActor` (as is `RoundStoreShared` and the watch's `AutoAdvanceMonitor`, which drives them): they are UI state, and every reader and writer must be on the main actor.
- `LocationManager` - GPS tracking (singleton)
- `WatchConnectivityManager` - iPhone-Watch communication (singleton)
- `SwingDetectionManager` - Motion detection (singleton, Watch only)
- `WorkoutManager` - HealthKit workout tracking (singleton, Watch only)
- `CourseDetailView` (iOS) - Per-course screen, reached by tapping a row in Stats → By Course. Sections: overview (rounds / scored / holes+par / last played), scoring (avg/best/worst vs par here), **By Hole** (each hole's avg vs par as a bar, plus avg putts — backed by `HoleStats` / `CourseStats.holeStats`, accumulated over qualifying rounds only so it matches the scoring numbers), rounds-here (→ `RoundsHistoryView(initialCourseFilter:)`), layout map, and Manage. **Manage is the app's only path to rename or delete a course**, and it appears only on the user's own courses: a shared (OSM) course is not theirs to change (`Course.isShared`, migration 00055; `DataStore.updateCourseInfo`/`deleteCourse` refuse one too) — `CourseEditorView` (reachable during play) edits holes only, and `DataStore.deleteCourse()` has no other caller. Before this, the screen was unreachable dead code: `CourseListView` was its sole call site and had none of its own after the Courses tab was removed, so no course could be renamed or deleted at all. That became a shipping problem once the manual round-start path started asking users to type course names. `CourseListView` is now deleted. Course rows whose `Course` row didn't sync still render but aren't tappable. The `runHoleDetectionAtRoundStart` / `runHoleDetectionWithTestCenter` toggles moved from here to **Settings → Developer** (long-press the Settings title) — they drive the satellite-blob analyzer, not the course.
- `DataStore.deleteRound` - Removes the round from the published array **and from SwiftData** (`context.delete`). The SwiftData delete matters: `loadRounds()` re-fetches the whole context, so without it a deleted round reappeared on the next launch and only really vanished when the Supabase delete echoed back through `RealtimeSync.applyRound(.delete)` — deleting offline, or missing that event, resurrected it. Cascade takes strokes and targets; `Round.holes` is `.nullify`, so the course keeps its holes. History (`RoundsHistoryView`) lists EVERY round including partials and zero-stroke starts — that's deliberate, it's where abandoned rounds get found and cleaned up — with swipe-to-delete and a holes-played line per row so partials are identifiable without opening them.
- `LocationPermissionBanner` (iOS, `Views/Shared/PermissionBanner.swift`) - Location-denied banner with an Open-Settings deep link, mounted on **`PlayTabView`**'s start screen. It previously lived on `HomeView`; when the tab bar became Stats/Play/History/Settings that view was orphaned, so the banner was unreachable and a denied user saw nothing — Start Round just fell through to the course-name prompt. `HomeView` is now deleted. Mount permission UI on the screen that needs the permission, not a hub screen.
- `StatsEngine` - Round/player statistics (iOS only). Computes per-round and per-club aggregates: avg score, putts/round, putts/hole, GIR%, avg tee-shot deviation degrees, plus per-club-type and per-club distance distributions. Tee-shot accuracy is reported as continuous degrees of deviation from the ideal bearing (no fairway-hit boolean threshold). **Round qualification gate**: a hole counts only with `minStrokesPerHole` (2) or more strokes — one stroke means teed off and walked away, and charging that hole's full par is what produced impossible negative scores (a single drive on a par 5 scored −4; a two-hole session scored −6). **Penalty strokes are strokes**: a hole's score is every stroke on it, penalties included (a hole of only penalty strokes scores their count), the same strokes the GIR test numbers by; only club distances skip penalties, since a penalty is not a shot. The scorecards, round detail and multiplayer players count the same way. A round then enters scoring stats only when its counted holes land in `scoredHoleCounts` (`{9, 18}`); everything else is a partial that stays in History and feeds nothing. This self-cleans rounds with unrecorded strokes — an 18 missing strokes on one hole lands on 17 counted holes and drops out on its own, no threshold tuning. **Scoring is bucketed by round length** (`PlayerStats.scoring18` / `.scoring9`, each a `ScoringStats`) because averaging a 9-hole score against an 18-hole score is a category error. **Club distances deliberately ignore the gate** — they accumulate from every round including partials, since a shot is a shot and more samples make the distribution better. `compute` takes `courses:` and resolves each round's pars via `courseId`, NOT `round.holes`: `Hole.round` is to-one, so older rounds' `holes` arrays drain as newer rounds at the same course adopt the shared instances, and reading `round.holes` silently zeroed the par for every round but the most recent one per course.
- `SupabaseManager` - Shared (iOS + watchOS) singleton wrapping the supabase-swift SDK's `SupabaseClient`. Exposes `auth`, `storage`, `realtime`, and `from(_:)` for Postgrest queries. Replaces the previous hand-rolled `SupabaseClient` / per-platform auth refresh logic. SDK manages session refresh, retries, and Realtime WebSocket lifecycle internally.
- `AuthManager` (iOS) - Sign In With Apple → SDK's `signInWithIdToken`. Listens to `auth.authStateChanges` and mirrors the session into `@Published session: AuthSession?` and forwards to the watch via `WatchConnectivityManager.sendAuthSession`. SDK handles token refresh internally — no hand-rolled refresh timer. The SIWA flow also captures `credential.fullName?.givenName` (Apple only ships this on the **very first sign-in** for the app, never again) and writes it via `PlaygroupService.upsertMyProfile(firstName:displayName:nil)` so multiplayer columns/headers can show real names instead of "Player." Existing-user fallback: editable name field in Settings → Multiplayer; the typed value goes into `display_name` (override slot) which beats the SIWA-captured `first_name`.
- **Settings → Developer shows both builds, because watch/phone skew is otherwise invisible.** The watch app is a separate binary that installs asynchronously after the phone's copy lands, and it can lag a long way behind. Neither app displayed what it was running, so a stale watch binary was indistinguishable from a bug in the current one — on 2026-08-27 a string removed in build 56 was still on the wrist because the watch was still on 55, and the only way to establish that was diffing the two commits. The watch now pushes `CFBundleVersion` through the `watchBuild` applicationContext key on every session activation; the iPhone reads it through `handleApplicationContext`, which also runs once at activation on `receivedApplicationContext` (see Modifying WatchConnectivity Messages). The row tints orange on mismatch. **A dash means the watch is running something older than the build that added this** (57) — it has never reported, which is itself the answer.

- **The watch needs the phone for CREDENTIALS, not for data.** This is the one real phone dependency and it is easy to misread. Clubs, types, sets, rounds, courses and strokes all come to the watch straight from Supabase over its own connection (`hydrateClubsFromSupabase`, `RealtimeSync`, `reconcileRoundsWithSupabase`) — WatchConnectivity carries none of them. But every one of those paths needs a session, and **Sign In With Apple only runs on the iPhone** (`AuthManager`), which forwards the session via `sendAuthSession`. `hydrateClubsFromSupabase` opens with `guard WatchAuthSession.shared.currentUserId != nil else { return }`, so with no session it returns silently and `availableClubs` stays empty. The home screen used to render that state as "Waiting for clubs to sync… / Open iPhone app", which named the wrong dependency — it implied the phone was slow to send clubs it was never going to send, when the watch was simply signed out and unable to say so. The gate now branches on `isSignedIn` first ("Sign in on iPhone") and only then on an empty bag ("Loading clubs…"). `WatchAuthSession.session` is `@Published` for this; note `onSessionChanged` is a single-assignment closure already owned by `WatchDataStore` for hydration, so a second consumer taking it would silently clobber the first.

- `WatchAuthSession` (watchOS) - Receives `AuthSession` updates from the iPhone via WatchConnectivity, feeds them into the SDK via `auth.setSession(accessToken:refreshToken:)`. Then the SDK is the authoritative refresh target. Everything from the phone enters through `receiveFromPhone`, which ignores a session it has already applied (matched by a SHA-256 of the refresh token in UserDefaults) unless the watch has none: the phone's context re-delivers the same session constantly, and re-setting it after the watch's SDK has refreshed would revive a spent refresh token and trip Supabase's reuse detection. `validAccessToken` / `forceRefresh` are thin wrappers around `auth.session` and `auth.refreshSession()`. Public surface preserved for SupabaseUploader/OSMCourseService callers.
- **Delete My Data** (Settings → Data, `SupabaseSync.deleteAllUserData`) calls the `delete-my-data` edge function, which removes the user's storage objects in every bucket (their folder exists in upper- and lower-case user ids) and then every row keyed to them (`delete_user_data`, migration 00057): rounds and their children, personal courses and holes, clubs, picks, motion events and test notes, false-negative captures, client events, playgroups they host, profile. Shared courses and the height map stay. `delete_my_data.sh` asserts it.
- `SupabaseSync` (shared) - Mirrors local writes to Supabase via the SDK's PostgrestClient (upsert, id-filtered update, delete). **Every write goes through one on-disk queue and is sent one at a time, oldest first (`pump`)**, so the server applies a device's writes in the order they were made; writes used to be concurrent requests, and a failed one retried after newer ones had landed could put an old value back. A write that doesn't reach the server holds the queue until the next write or the 30s retry tick; one the server refuses outright (`isPermanent`: PGRST1xx/2xx, SQLSTATE 22/23/42) is dropped and logged as `supabaseSync.write.rejected`, since it would otherwise block everything behind it forever. A write to the same row as the last queued one merges into it while it waits. `hasPendingWrite(table:id:)` is what `RealtimeSync` uses to hold a row this device hasn't had confirmed.
- `OSMCourseService` - Shared (iOS + watchOS). Two-pass design: `fetchCandidates(near:)` runs `way[leisure=golf_course][name](around:R,...)` + `relation[leisure=golf_course][name]` and returns named `OSMCourseCandidate` features (centroid + bounding polygon). `fetchCourseGeometry(for: candidate)` is polygon-scoped — `way["golf"="hole"](poly:"...")` etc. — pulling holes/greens/tees/fairways/bunkers inside a specific picked course; a round uses it only when `register-osm-course` (which builds the same data on the server, from the OSM API, and stores it on `courses.osm_polygons`) cannot be reached. Cross-user shared per ODbL — attribution surfaced in `SettingsView.swift` Credits section. Both phone and watch call directly without WatchConnectivity.
- `AutoAdvanceMonitor` (watchOS) - Throttled (2s) location subscriber. **Putted-then-left** logic with a single ephemeral `currentHoleEnteredAt` timestamp — resets on every `currentHoleIndex` change in any direction (forward auto-advance, manual back-nav, manual forward-nav, fresh load). No per-hole sets, no maintained flags, no `completedHolesArray` gate. Gates: (1) **putt-since-arrival** — there exists a putter stroke for the current hole with `timestamp > currentHoleEnteredAt` (filters out old putts from prior visits, kills back-nav re-fire); (2) **distance** — user is `>= greenLeftThresholdYards` (10yd default) from the green polygon edge (source-agnostic — OSM Tier-1/2 polygon or blob-detection polygon matched by hole-marker containment in `WatchDataStore.filteredGreenCandidates`); (3) **bonus accelerator** — when OSM provides next-hole tee data, also fires when user is within `teeBoxThresholdYards` (10yd) of the next tee centerline. All distances in yards. Toggleable via `enabled` (persisted in UserDefaults, default on). **Thresholds set by Jared, not invented.**
- **One round at a time, reachable from either device.** Both `DataStore.startRoundAtCurrentLocation` and `WatchDataStore.startRoundAtCurrentLocation` now `await RealtimeSync.reconcileRoundsWithSupabase()` and abort (logging `round.start.abortedExistingRound`) when a round already exists. `startRound`/`performStartRound` call `endAnyOngoingRound` unconditionally, so starting on one device while the other's round hadn't synced yet created TWO live rounds — both upsert, and each device's `currentRound` picks the most recent by date, so the two could disagree about which round is being played and a device could jump to the other's empty round mid-round. `PlayTabView` also reconciles `.task`-on-appear and offers `.refreshable`: Realtime normally delivers a watch-started round, but postgres-changes don't replay across a dropped socket and the only other catch-up was `scenePhase → .active`, which never fires when the phone was already open. `RealtimeSync` refreshes the cached arrays (`loadRounds`/`loadCourses` on iOS, `refreshCurrentRound` on watch) after applying, which is what makes `currentRound` — a computed filter over those arrays — actually update.
- `RoundLifecycleEvaluator` (shared, iOS + watchOS) - Pure function returning whether an in-progress round should be auto-ended. Two conditions: (a) `Round.lastActivityAt` more than **1 hour** ago (no strokes added, no hole-index changes — purely wall-clock check, no GPS needed) or (b) user is **>2km** from every hole's coordinate on the round (off-course, requires a GPS fix and at least one hole with coordinates). **Inactivity decisions are server-verified before acting** (`serverLastActivityAt`): the local `lastActivityAt` can be arbitrarily stale when the other device was the writer while this one was backgrounded (Realtime doesn't replay missed events, and the sweep fires immediately on launch/foreground) — the May 31 Wekiva round was wrongly auto-ended mid-play exactly this way. Offline fallback trusts the local value, preserving the old behavior. Both `DataStore` and `WatchDataStore` run a 60s `Timer` that evaluates the current round and routes a positive result into the platform-specific `endRound`. The watch sweeps even when the phone is asleep and vice versa. Manual `End Round` buttons (Watch `OptionsView`, iOS round-summary `EndRoundButton`) and the auto-end-prior path in `startRound` route through the same `endRound`. Setting `Round.endedAt` is the single source of "this round is finished" — both `currentRound` getters filter `endedAt == nil`, so an ended round disappears from "Continue Round" everywhere immediately.
- `WatchDataStore.filteredGreenCandidates(for:)` (watchOS) - returns the green-candidate list the labeling UI consumes. Two sources, in priority order: (1) **OSM green polygons** when round was resolved with OSM data — converted to `HoleDetectionBlob` shape with synthetic high filter scores so they always pass; (2) **blob detection results** filtered by `holeFilterSettings`. Tier-2 rounds (greens present but holes weren't cleanly numberable) get OSM polygons here instead of blob output. **Blob delivery is server-first**: at blob-request time the watch checks `courses.blob_detection_results`, and on a miss it sends the WC analyze request *and keeps polling the server cache every 10s through the 60s pending window* — the iPhone analyzer typically uploads in ~20s, but its WC push is a >50KB file transfer (opportunistic, can lag minutes), so a single up-front check loses the race (seen live at Wolf Hollow 2026-07-05: upload landed 22s after the only check; the picker opened empty). Every delivery path (up-front hit, pending poll, WC receive, resume hydrate) funnels through `applyBlobDetectionResults`, which also re-asserts `Round.holeDetectionEnabled` via `ensureHoleDetectionEnabled(forCourse:)` — a cross-device round upsert can clobber the flag back to false after the watch flips it on at request time (the iPhone reconcile races the flip), and the `AddHoleNavigationView` picker gate returns zero candidates while the flag is off. **iOS `DataStore` exposes the same trio (`filteredGreenCandidates`, `osmCourseData(forCourseId:)`, `getTypeName(for:)`)** so the iOS play map (`HoleMapView`) can render the same green-polygon outline, OSM centerline, and "Putts: N" annotation as the watch — single shared signature, no platform-specific UI helpers.
- `GhostRoundStore` (shared, `@MainActor`, lives in `RoundPathCache.swift`) - "Ghost round" overlay: the user's most recent COMPLETED non-test round at the same course, rendered under the live hole map as a dim dotted grey walk path + dimmed grey stroke markers labeled with each shot's DISTANCE (to the next non-putt stroke; the final approach shows distance to the first putt) — putts are filtered out of the markers exactly like the live stroke rendering. Toggles: watch Options "History" row (above Home), iOS floating-button left stack (clock.arrow.circlepath, blue when on); preference persists in UserDefaults (`ghostRoundOverlayEnabled`). Resolves the ghost round once per (course, active-round) pair — most recent `rounds` row by this user at the course with `ended_at` set, `location_test_mode_enabled != true`, **and at least one stroke recorded** (the stroke-existence gate is the primary filter: the per-round test flag is legacy and unreliably stamped, and a stroke-less round — queue-drain throwaway, abandoned at the first tee — is never a useful ghost), excluding the active round — then lazily fetches per-hole `round_altitude_readings` (path) + non-penalty `strokes` on appear/hole-change (watch `loadGhostForCurrentHole`, iOS piggybacked on `refreshBreadcrumb`). Render sites: watch `ActiveRoundView` map (after the OSM centerline block), iOS `HoleMapView` (before the breadcrumb trail).
- `RoundPathCache` (shared, `@MainActor` — compiled into BOTH targets, not iOS-only) - In-memory cache of breadcrumb path samples per `(round_id, hole_number)`, pulled on demand from `round_altitude_readings`. Drives the iPhone breadcrumb display when reviewing any hole — current hole during a live round (refreshes on every hole-change with `forceRefresh=true`, up-to-30s stale matching the watch's flush cadence), prior holes during a live round (cache-first since the data is settled), or post-round. Same DB-as-truth path serves all three cases — no WatchConnectivity GPS plumbing needed since the watch already uploads to the table. `HolePlayView.refreshBreadcrumb()` calls `loadIfNeeded` on appear and on hole change; `HoleMapView` renders the fading-dot trail from the cache in the user's playgroup color, identical styling to the watch's breadcrumb.
- `ElevationReadout` (shared, iOS + watchOS, `@MainActor`) - `@Published deltaToGreenMeters: Double?` for the active hole, drives the live "↑/↓ ft to green" display. `deltaMeters(to:)` is you → a point (target markers); `deltaMeters(from:to:)` is a shot's own rise/fall from the historical cell map, which every stroke marker (watch `ActiveRoundView`, phone `HoleMapView`) labels via `ElevationDeltaLabel(shotFrom:shotTo:)` — from where the shot was hit to where the next was played, or to you for the latest. Stroke markers used to pass `coordinate:`, so an uphill drive's tee marker read ↓ once you reached the ball. Subscribes to `LocationManager.$pathSamples` and on each emission: (1) **calibrates** the round's altimeter offset (`cLive`) via a time-decayed weighted average of crossings between this round's path samples and the cached cell map, with a 5×5 weighted neighborhood per sample (center 4 / ring1 2 / ring2 1) and exponential time-decay `exp(-age/τ)` (τ default 25 min, dev-menu configurable via `elevationCalibTauMinutes`); (2) computes target elevation via the same 5×5 weighted neighborhood blend at the green centroid, weighted by `n_samples × proximity` — no display gate, every cell contributes proportionally to its accumulated sample count; (3) computes user elevation via tiered blend — historical neighborhood at user's position + bucketed user-path neighborhood (no time-decay since same-location implies recently visited) + last-resort `latestRelAlt + cLive`. Honors `LocationManager.isTestModeEnabled` (no readout in GPS-sim mode). `start(courseId:)` is called from `startRound` after `HoleHeightCellCache.loadForCourse` finishes; `updateHole(number:green:)` is pushed by the play view on hole-index changes. `start` preserves an already-pushed hole — the play view's `.onAppear` usually fires `updateHole` before the async cache load completes, and the old wipe-on-start left the readout blank on the round's first hole. The `Hole.coordinate` (green centroid) should be non-nil under normal play; if it's nil the readout silently disappears, which would indicate a missed guard in the play view. **Display**: `ElevationDeltaLabel` (shared, `GolfTracker/Views/Shared/ElevationDeltaLabel.swift`) renders the compact "↑3"/"↓7" feet label; Display differs by platform: **watch** — the single big yardage number in `ActiveRoundView+GPSIndicator.holeInfoOverlay` TOGGLES between measured and plays-like on tap; plays-like mode is signaled by COLOR only, the number wearing the same tint as the elevation delta (red uphill / cyan downhill via `ElevationDeltaLabel.color(forFeet:)`), white = measured; preference persists via `@AppStorage("yardageShowsPlaysLike")`; falls back to measured when plays-like isn't computable — putter, no elevation solution, test mode — and on-green bright-green keeps priority over the mode tint; the small ↑/↓ delta stays beside it in both modes; **iOS** — `PlaysLikeStack` (same file as the label) stacks a "≈N" plays-like yardage over the delta label beside the big yardage in `HoleOverlayControls`. **Plays-like is club-trajectory-aware** (`PlaysLike` enum, same file): adjusted = distance + Δh/tan(landing angle), with the landing angle keyed by club-type name from the published TrackMan tour averages (Drive 38°, 3-Wood 43°, Hyb 47°, 4-Iron 48° … 9-Iron 51°, Pitch 52°, Gap 53°, Sand 54°, Lob 55°; unknown names fall back to the classic 45° = 1-for-1; putter → no plays-like, rolling-ball physics). The name parser is fragment-based to catch both the terse default type names and user-defined variants. Watch passes the selected club (always present); iOS has no club selection on the play screen so it shows the **self-consistent best candidate** — `PlaysLike.bestCandidate` scores each club type against the plays-like number computed with that club's OWN angle ("does this club's shot match the shot I need"), immune to selection feedback loops. **Club prediction uses the same self-consistent scoring**: `ClubPredictionManager.predictClubIndex` takes `deltaMeters` and matches club averages against per-candidate plays-like rather than raw distance (`applyClubPrediction` passes `ElevationReadout.deltaToGreenMeters`). Tour angles slightly under-adjust amateur trajectories (shallower flight) — a flat amateur offset or per-club empirical fit from stroke history are the planned refinements. Falls back to the bare delta label when no distance/putter, disappears entirely when the readout has no solution.
- **`ClientEventLogger` has two tiers; lifecycle is always on.** It used to be entirely behind a UserDefaults toggle that defaulted OFF, so the app's normal state was to keep no account of itself — which is why the 2026-08-21 elevation failure had to be reconstructed from raw `round_altitude_readings` instead of read off `elevation.field.loaded`. It cannot simply be switched on, either: measured over the 2026-05-08 round (the only full round it ever ran), it wrote **131,954 rows in a day**, 84.5% of it from the 100 Hz detector path — `unif.bsTop` alone is ~51,000 rows per round and `unif.fsPeak` ~42,000. That volume is a battery and egress problem, not telemetry. So `log(_:level:detail:force:)` now takes a `Level`: `.lifecycle` (default, always records, ~2,800 rows/round ≈ 23 a minute — round lifecycle, elevation cache, uploads, errors) and `.diagnostic` (still gated on the toggle — everything in the detector loop or on a periodic timer: all `unif.*`, all `rawAccel.*`, `watch.diagnostics.tick`, `green.state`). `level` precedes `detail` in the signature so existing call sites needed no edit. **When adding a log call, ask what it costs per round**: anything that can fire more than a few times a minute is `.diagnostic`.

- **No elevation solution renders a dash, never nothing.** `ElevationDeltaLabel` used to draw an empty view when `deltaToGreenMeters` was nil, which made "no answer" pixel-identical to "this hole is flat" — a genuine zero prints `↑0` in dim white, and empty space next to a 32 pt yardage reads the same at a glance. That ambiguity is what let the 2026-08-21 truncated-map failure pass as a flat course for a whole round. Nil now prints `ElevationDeltaLabel.noSolutionGlyph` (`–`) in `noSolutionColor` (`white.opacity(0.35)`, dimmer than flat's 0.7): not an arrow, not a digit, unmistakable for a reading of any magnitude. `↑0` means the green is level with you; `–` means the feature has nothing to tell you. Applies on both platforms — the label is shared.

- **`hole_height_cells` is addressed by POSITION, never by hole** (migration 00045) - The primary key is `(course_id, cell_lat, cell_lon)`. It used to be `(hole_key, cell_lat, cell_lon)` with `hole_key = lower("<course_id>:<hole_number>")`, which was correct under the original per-hole frame model (00037's header: each cell held an altitude "in the hole's shared reference frame") and became a liability the moment 00044's global re-solve gave every course a single datum. **A reading's `hole_number` is app UI state, not survey data** — it is whatever hole `AutoAdvanceMonitor` was counting at capture time, and its triggers B and C fire on proximity to the next hole's centerline or to a historical first-stroke spot with **no putt gate**. When it advances early the readings still land on the right ground and got filed at the wrong address: at Hyde Park every reading on hole 15's green carries the label 16, so a lookup at 15 found nothing (nearest cell 37.1 m) while 16 carried a phantom blob 144 m from its own green. Worse, because the hole was part of the PK, one 3 m square could exist twice under two holes with two different heights — 14 such squares existed across the two mapped courses, disagreeing by up to 4.61 m where the true difference is zero by construction, with neither copy carrying the full sample count. After the migration hole 15's nearest cell is 0.1 m. The hole number now lives only where it belongs: as the hole currently in focus, naming which green centroid from `holes` the yardage is measured to. **The math never sees it.** `ElevationFoldIn.holeKey` and the old lowercase-normalization hazard from 00043 are gone with it.
- **Elevation lookup radius is asymmetric** — `ElevationReadout.userCellRadius` (±2 cells, ~6 m) for the USER's position, `targetCellRadius` (±4, ~12 m) for the GREEN. A green is 20-30 m across, so cells 12 m from the centroid are still on the putting surface; the centroid is an OSM or hand-placed point rather than somewhere anyone necessarily walked, so a ±6 m window frequently found nothing and the readout silently vanished. Measured on Hyde Park's map: ±6 m gave a readout on **7 of 18** holes, ±12 m gives **12 of 18**, and holes that already worked barely move (hole 5 −2.28 → −2.29 m), confirming the wider window samples the same surface rather than smearing into terrain. The user stays tight because tiers 2/3 cover them with their own live path samples.
- `HoleHeightCellCache` (shared, `@MainActor`) - Loaded once at round start from the **`course-height-field` edge function**, held as a flat `[CellKey: ExistingCell]` for the whole course (it used to group by `hole_key`, so a lookup near a green could miss cells sitting a metre away under a neighbouring hole's key). Read-only during the round. Not refreshed mid-round — multi-user co-folding is rare enough that the freshness penalty is acceptable in exchange for a network-free read path during play. Wiped on `endRound`; the disk copy survives.
- **Nothing reads `hole_height_cells` from the client. PostgREST silently truncates at 1000 rows.** This is not a style preference — it cost a whole round. `HoleHeightCellCache.loadForCourse` used to `select()` the table with no range; on 2026-08-19 the field solver rewrote Hyde Park as 5107 cells in one shot, and the round played there two days later had **no elevation readout on any hole** because the watch received the first 1000 cells and every unreturned cell reads as ground nobody has walked. Replayed against that truncated map, 0 of 1079 ticks on holes 1-9 resolve a user elevation and no green resolves at all; against the complete field, 100%. The failure is silent by construction — a short read is indistinguishable from a sparse map, and the `↑0` the label would show at zero delta renders identically to the nothing it shows when the value is nil, so "flat course" and "broken" look the same on the wrist. **Two sibling reads had the same bug**: `ElevationFoldIn.attempt` pulled a round's own `round_altitude_readings` unbounded (a 9-hole round is ~1400 rows, 18 holes ~2400), so every client fold-in solved its offset from the first third of the round; and `ElevationFoldIn.foldInCourse` read existing cells unbounded, solving against a fifth of the map. Both fixed — the readings read pages via `ElevationFoldIn.readPageSize`, the cells read goes through the endpoint. `HistoricalFirstStrokeCache` is paged for the same reason (it grows one row per hole per round forever). **Any new read that can exceed 1000 rows must page or go through a function that does.**
- **`course-height-field` serves the map as a field, not as rows.** One POST, complete by construction (paged server-side), `~10` bytes per cell against `~85` as JSON — Hyde Park 483 KB → 78 KB, measured. Payload is `sparse-v1`: little-endian, 10 bytes per cell, `int16 di, int16 dj, float32 altM, uint16 n`, offsets relative to a `originI`/`originJ` minimum corner, base64'd. Sparse rather than dense because Hyde Park's cells occupy 5816 of the grid's ~109k slots (5.3%) and densifying would inflate the payload sevenfold to carry mostly holes. The client verifies the server's `step` against `ElevationFoldIn.cellStepDeg` and **refuses a mismatched payload** rather than quantizing every cell into the wrong bucket. Round-trip verified against the table: identical key sets, altitude agreement to 0.0002 mm, zero `n_samples` mismatches. **Revalidation**: the client sends its cached `haveSolvedAt` (from `hole_height_solves`) and gets `{unchanged:true}` in 114 bytes when the map hasn't been re-solved, which is the common case since the map only moves when a round folds in.
- **The lookup stays on the device on purpose.** `ElevationReadout` recomputes on every path sample — ~5.6 s apart, ~1400 times over a round — and a golf course is exactly where the watch has no signal. A per-tick edge-function call would be slower, drain the battery, and go blank whenever coverage does. Fetch the field once, evaluate locally. `HoleHeightCellCache` is also **disk-backed** (`Caches/HeightFields/<courseId>.json`, same wire encoding): the fetch is one shot at round start with no retry, so a hiccup at the first tee used to mean no readout for the whole round with no way back. The last good field is adopted first and then revalidated, because terrain does not move and a stale map is only ever wrong by the rounds folded in since.
- **The re-solve runs automatically at round end, on BOTH paths.** `ElevationFoldIn.requestGlobalResolve` POSTs the round's course to the `resolve-hole-heights` edge function after every fold-in attempt — deliberately outside the `catch`, because the rounds that FAIL to fold in are exactly the ones that couldn't solve an offset against the existing map, and a global re-solve is precisely what rescues them (it has every round's readings, not one round against a fixed map). Gating it on fold-in success would withhold it from the case that needs it most; the raw readings are uploaded either way, so there is always something to solve. Best-effort and non-fatal: the fold-in has already refreshed the map, so a failure costs freshness, not data, and the function is idempotent (it replaces a course's cells wholesale from `round_altitude_readings`) so repeated or concurrent calls converge. Auth is the user's session JWT; the function verifies it and then uses service-role internally, since `replace_course_height_cells` is revoked from `authenticated`.
- **`ElevationReadout.minCalibrationSupport` (2) gates CALIBRATION, not display.** Since the map became a solved field every cell has a value, including ground that was barely walked — fine to display, unacceptable to calibrate against, because that value folds straight into `cLive` and then rides every later estimate until the next crossing. Averaging many crossings does not rescue it: that removes noise in the OFFSET, not the error in the cell you are standing on. Mirrors the server solve's own minimum node support. The TARGET lookup deliberately does not gate — a green centroid is a reasonable place to interpolate a few metres and refusing there would just blank the readout. Measured on the live Hyde Park map: 5086/5107 cells pass, so it rejects the barely-observed fringe rather than starving the readout.
- `ElevationFoldIn` (shared) - Round-end fold-in into the shared `hole_height_cells` table, **once for the whole course** (was once per hole; see the addressing bullet above). Pulls the course's existing cells, finds spatial crossings, solves a 1-variable weighted offset (closed-form weighted mean), buckets corrected readings into 3 m cells, RPCs `upsert_course_height_cells` to atomically merge with concurrent client writes. **Skips the fold-in when cells exist but this round crossed none of them** — now a course-wide test rather than per-hole, which is the point: a round that crossed nothing on hole 7 but plenty on 1-6 used to have its hole 7 data discarded despite its frame being fully determined. Because the fold is one atomic RPC, a failed attempt leaves nothing half-written and the pending marker no longer needs per-hole progress tracking. Reads the course's existing cells through `HoleHeightCellCache.fetchField` (never the table directly — see the row-cap bullet above) and its round's readings in pages. **Durable**: entry point is `run(courseId:roundId:)`, which persists a pending marker (UserDefaults) before any network work and records per-hole successes; `retryPending()` runs on app foreground on both platforms and re-attempts without double-merging. The watch's `endAnyOngoingRound` also routes auto-ended rounds through `run` (it previously skipped fold-in on that path). **All cell dictionary keys are integer cell indices** (`ElevationFoldIn.cellIndex`), never quantized Doubles — raw-Double keys missed ~34% of 5×5 ring lookups from last-ULP float differences.
- **The server solve (`resolve-hole-heights`) is in the algorithms package repo**, with its tests, its constants and the account of how it models the map (`StrokeSaverAlgorithms/CLAUDE.md`). What the app relies on: it rebuilds a course's cells wholesale from `round_altitude_readings` (so repeated or concurrent calls converge), it publishes the same 3 m cell grid the client reads (`ElevationFoldIn.cellStepDeg`), and each cell's `n_samples` is accuracy-weighted support, which `minCalibrationSupport` gates on.
- **Course holes: shared and personal** (migration 00053). A `holes` row is **shared** (`owner_id` null) only when it comes from OSM data that determines the hole order — the course's stored `osm_polygons` has integer refs exactly `1..N`, the resolver's `full` tier. Every signed-in user reads shared holes and **no client can insert, update or delete one**: they are built on the server by `derive_osm_course_holes(course_id)` from the course row's own `osm_polygons`, which `RoundResolver` (after storing a new course) and `DataStore.courseForRound` (an existing course with no holes) request through `SupabaseSync.deriveOSMCourseHoles`. **Every hole a user places or moves is personal**: owned by them, invisible to everyone else. Clients write personal holes only through `upsert_my_course_hole` / `delete_my_course_hole`, keyed on (course, caller, number) — the local hole being edited may be the shared row, whose id is taken, so the local id is only a suggestion for a new row (`SupabaseSync.upsertMyCourseHole`, which queues RPCs in the same ordered write queue as everything else). So moving a shared green gives the user their own hole for that number, and the course then has both rows; on every device the user's own wins (`RealtimeSync.applyHole` refuses a shared row where the course holds the user's hole for that number; `fetchAndInsertCourse` and the elevation fold-in's green read pick it the same way). `Hole.ownerId` mirrors `owner_id` locally. **Renumbering and deleting holes rewrite every number, so `CourseEditorView` offers them only on a course with no shared holes** (`DataStore.canRenumberHoles`). The rules are asserted against the live project by `supabase/tests/holes_rls.sh`. Where a green placed by hand comes from: the watch's placement (`HolePlacementView.save`) stores it on the pick and as the user's own hole; at a course OSM has never heard of (Wolf Hollow, 15 greens placed and no rows until 00046 backfilled them from `round_holes`), those personal holes are the only greens there are, and the elevation readout targets them. **`course_hole_picks` cross-user voting is separate and still shared**: three or more users agreeing on one detected blob id seeds that green for others (`WatchDataStore.fetchCanonicalHolePlacements`), and every pick row, coordinates included, is readable by any signed-in user.
- **Vehicle guard: the drive home is cut before it reaches the map.** `ElevationFoldIn.dropVehicleTail` drops the tail of a round from the first sustained run above `vehicleSpeedMps` (9 m/s over a 15 s window), because a phone in a car reads cabin pressure, not altitude. The server solve applies the same cut with the same constants, and uses the same cell grid; `Tests/AppLogic`'s `SharedConstantsTests` fails when `ElevationFoldIn`, `course-height-field` and the solver disagree, since the client would otherwise seed cells the re-solve then discards.
- `LocationManager.PathSample` (shared) - Each path sample carries `(coordinate, timestamp, relAltMeters, sampleCount, holeNumber)`. **`relAltMeters` is the MEDIAN (not mean) of the ~1 Hz barometer readings in the sample's window** — the wrist barometer reads wrist height, and bend-downs (teeing up, ball retrieval; reads ~1 m low) and wrist-raises (reads high) are 2-3 s transients that are a minority of a window's readings, so the median never elects them; the old mean let them systematically bias tee and cup cells in the height map. The `holeNumber` is captured at append time from the recording context's provider closure — same value goes onto the in-memory sample and the upload row, so both stay aligned even if the provider's value changes between calls. **Path-upload flush hardening (2026-07-06)**: the 30s flush's `pathFlushInFlight` guard is deadline-protected — a hung upload request once held the flag for an entire round (2026-07-05: uploads stopped 13 min in; every later tick early-returned; holes 2-15 queued on disk but never flushed). Now the request itself is raced against a 30s timeout (loss = normal failure, chunk requeues), ticks reclaim a flag held >90s, and the upload is an **ignore-duplicates upsert on the row's client-side UUID** (was a plain insert) so a timed-out request that lands server-side anyway can't make the retry fail with a conflict. The disk queue is the recovery path: rows persist at capture time and drain at the next `startPathRecording`. The `forceFullGPSKey` UserDefault (dev-menu toggle "Force full-fidelity GPS during round") coerces every `setGPSPowerMode` call to `.full` for the round's duration, bypassing the distance/putter heuristics that drop to `.moderate`. Useful for elevation calibration validation, where 10 m GPS noise can push samples into adjacent 3 m cells and miss historical crossings.
- `RealtimeSync` - Shared (iOS + watchOS) singleton. Subscribes to Supabase Realtime postgres-change streams (`rounds`, `courses`, `holes`, `round_holes`, `strokes`, `targets`, `club_types`, `clubs`, `club_sets`) on a single channel `user:<uid>`. INSERT/UPDATE/DELETE events apply to the local SwiftData store via per-table `apply*` methods (UUID match → upsert, delete on .delete). After save, fires `objectWillChange.send()` on the platform DataStore (`WatchDataStore.shared` on watchOS / `DataStore.shared` on iOS) so views using computed properties like `currentRound` re-render — without this hop, hole-index changes pushed from one device wouldn't reflect in the other device's view until manual navigation. **Lifecycle**: iOS keeps Realtime always-on once signed in (started/stopped from `AuthManager.authStateChanges`; `HolePlayView.onAppear` also starts it, idempotently). Nothing else stops it: the phone is the watch's live link to the server (`relayRow`), and `HolePlayView.onDisappear` used to call `stop()`, which cut the watch off whenever a round ended and Play closed. **Concurrency**: the class is `@MainActor` because every `apply*` writes the platform DataStore's single `ModelContext`; before that, each per-table stream loop applied changes on its own cooperative thread and bursts across tables crashed SwiftData. `start`/`stop` are chained through a `lifecycle` task so a teardown and a restart never interleave (they did on leaving Play and returning, and crashed in `RealtimeChannelV2.status`). Teardown calls `realtime.removeChannel`, not `unsubscribe`: the client caches channels by topic and would hand the dying channel back to the next restart. **Keep supabase-swift at 2.47.2 or later** (pinned 2.55.2): earlier versions re-ran the connected handler on any duplicate connect — two channels subscribing at launch was enough — which dropped the message listener, so every frame was lost until the heartbeat timed out ~52s later (the first-attempt "Maximum retry attempts reached" failures since August; fixed upstream as SDK-959). The app makes no explicit `realtime.connect()` calls — the channel subscribe connects the socket itself. **watchOS only opens the channel when a multiplayer playgroup is active** — `startPlaygroupChannelIfNeeded` in `ActiveRoundView.onAppear` gates the `start()` call on `PlaygroupService.currentOpenPlaygroup() != nil`. Solo rounds on the watch never open the WebSocket; watchOS Realtime was unreliable in earlier testing (especially non-LTE). The watch still receives every change live: the phone forwards the rows it applies (`relayRow` / `applyRelayed`). Sign-out tears down. Outside of rounds the watch relies on `WatchDataStore.hydrateClubsFromSupabase()` for clubs/types/sets (called at watch startup, on session-changed, and on `WatchHomeView.onAppear`). **Catch-up reconciliation**: postgres-changes are live-only — they don't replay events missed during socket gaps or backgrounding. `reconcileRoundsWithSupabase()` pulls recent rounds (8h window) + their `round_holes`, `strokes`, `targets`, **and the rounds' `courses` + course `holes`** via Postgrest and upserts through the same `apply*` path, then makes each of those rounds' holes, strokes and targets exactly the server's (`removeLocalRowsMissingFromServer`): something deleted or undone on the other device while this one wasn't listening is removed here, since a delete isn't always delivered live. It keeps rows with an unconfirmed local write and the holes of a round whose `round_holes` rewrite is pending. The hole, stroke and target fetches throw rather than falling back to empty, because an empty fetch would trim everything. **An older copy of a row never replaces a newer one.** Rows reach the watch through the phone, and one queued by `transferUserInfo` while the watch was out of reach can land after a newer copy; each synced model (`Round`, `Hole`, `Stroke`, `Target`) keeps the `updated_at` it last applied as `serverVersion` (microseconds, `RowVersion`), and `applyRound`/`applyHole`/`applyStroke`/`applyTarget` drop an incoming copy older than that (`realtime.apply.staleDropped`). A copy with no `updated_at` always applies. Migration 00054 makes the server stamp `updated_at` on every write to those tables (and gives `round_holes` the column), so it is the order rows were written in rather than the sender's clock. A delete is not versioned: a stale copy of a deleted row recreates it until the next catch-up removes it. **A row this device still has an unconfirmed write for is never overwritten** by an incoming event or a catch-up row (`SupabaseSync.hasPendingWrite`): the incoming version predates the write, and the write's own echo brings the row as it ends up. The course pull matters: a round recovered via reconcile is unrenderable in `PlayTabView` without its course row, and the live `courses` INSERT fires exactly once (at resolve time), typically while the phone is backgrounded — this was the "watch round exists but the phone Play tab says Ready to Play" gap. Fires from three places: sign-in (AuthManager), app foreground (`scenePhase == .active` in GolfTrackerApp), and after every successful `subscribePersistently` (re-)subscribe via the new `onSubscribed` callback in RealtimeReconnect. **History**: `syncMissingRoundsWithSupabase()` is the only path that downloads past rounds — it diffs the server's round ids against the local store and pulls the missing rounds with their `round_holes`, `strokes`, `courses` and course `holes` (paged, since PostgREST truncates at 1000 rows), then `rebuildPlayerStats`. Without it a reinstall or new phone saw an empty History/Stats, and a watch round played while the phone app was closed past the 8-hour window never arrived. iOS runs it right after reconcile at sign-in and on foreground; it is one id query when nothing is missing. It only adds — a local round the server lacks is left alone, since its upload may still be queued. **Orphan repair**: when child rows arrive before their parent Round, `Hole`/`Stroke` are inserted with `roundIdRef` set but `round` nil; `applyRound`'s `adoptOrphans` re-attaches them when the parent finally lands. This eliminates a silent-drop class of bug where out-of-order delivery left children disconnected from `round.holes`/`round.strokes` forever.
- `ScorecardView` (shared, in `GolfTracker/Views/Shared/`) - Vertical scorecard with two layouts. **Solo** (default, also when in a 1-person playgroup): rows = holes, columns = Hole / Par / Tee yardage / Score. Compiled into both targets — used on iOS via the `showingRoundSummary` sheet from `HolePlayView`'s floating buttons, used on watchOS via the scorecard button on the right side of `ActiveRoundView`.
- `ScorecardSheet` (shared, in `GolfTracker/Views/Shared/`) - Async-loading wrapper around `ScorecardView`. Two parallel `.task`s: one keyed on `round.selectedTeeId` loads the local user's cached tee data (`course_tees` + `course_tee_holes`); a second keyed on `PlaygroupChannel.activePlaygroupId` calls `playgroup.fetchScorecardPlayers(...)` to assemble the multiplayer payload (self from local Round + concurrent fetches for each co-member's round/strokes/tee), passing the result as `players` into `ScorecardView`. When not in a playgroup, the `players` array stays empty and the solo layout renders unchanged. Live updates: `.onChange(of: playgroup.otherStrokes)` and `.onChange(of: round.strokes.count)` re-trigger the multiplayer fetch so the sheet stays current while open without the user closing + reopening.
- `PlaygroupService` - Shared (iOS + watchOS). Multiplayer host/join/accept/decline/end + member discovery + profile reads. Exposes a 6-color `playerPalette` for per-member assignment (host gets palette[0], next joiner palette[1], etc.). `hostPlaygroup(...)` captures the host's current GPS into `playgroups.host_lat`/`host_lon` (migration 00015) so joiners can be filtered by proximity. `nearbyJoinable(currentLocation:)` is GPS-gated: returns empty if the joiner has no GPS yet, otherwise filters open playgroups to those whose host coords are within `nearbyMaxMeters` (100m) — multiplayer is only for people physically together at the same course. Profile writes are not handled here (no SIWA→profiles flow yet); only reads via `profiles(for:)`.
- **Playgroup auto-close** — `pg_cron` job (migration 00018) runs hourly server-side and closes any playgroup with `status='open'` AND `started_at < now() - 6 hours`. Member rows and strokes stay untouched (history is preserved); only the playgroup row's status / closed_at / ended_at flip. No client involvement, no Edge Function, no notifications. 6h is intentionally generous — average rounds are 4-4.5h.
- **Playgroup `round_id` attachment** - `PlaygroupService.attachMyRound(playgroupId:roundId:)` points the caller's own `playgroup_members` row at the round they're playing, called from `PlaygroupChannel.start` (before its already-running guard, so it still fires when the round changes inside a live playgroup). **This is load-bearing, not housekeeping.** The host gets a `round_id` at `hostPlaygroup` time, but `acceptRequest` inserts a joiner with `round_id = nil` — the host can't know the joiner's round and join requests don't carry one. While it's nil the joiner is invisible to everything keyed on their round: `fetchScorecardPlayers` filters them out, leaving one player, which is below `ScorecardView`'s `players.count >= 2` threshold, so the **shared scorecard silently renders as a solo card**; and no stroke subscription is wired, so their shots never appear. Presence/live dots still worked throughout, which is what made the gap look like a working feature. RLS `pm_update_self_or_host` already permits self-updates, so no schema or policy change was needed; co-members pick it up via the existing `playgroup_members` postgres-changes subscription.
- `PlaygroupChannel` - Shared (iOS + watchOS) singleton (`@MainActor`-isolated, `ObservableObject`). Owns the `playgroup:<id>` Realtime channel for the user's current open playgroup. Three responsibilities: (1) **Presence (live dots)** — every 5s while `liveDotsEnabled` (UserDefaults, default true), publishes `{user_id, lat, lon, ts}` via `channel.track(state:)`; subscribes to `presenceChange` and exposes `@Published presence: [String: MemberPresence]`. (2) **Other-player strokes** — fetches members of the playgroup, then pulls each non-self member's strokes for the current hole via PostgREST. Subscribes to postgres-changes on `strokes` filtered to those `round_id`s for live updates. Stored in-memory in `@Published otherStrokes: [String: [RemoteStroke]]` — NOT written to SwiftData, since those rounds aren't owned by the local user. (3) **Members snapshot** — `@Published members: [PlaygroupMember]` for color lookup via `color(for: userId)`. Live: subscribed to postgres-changes on `playgroup_members` filtered to the active playgroup id. Mid-round joins/leaves trigger `refreshMembers` which refetches the list, wires stroke postgres-changes for any newly-present `round_id`s (tracked via `wiredRoundIds` to avoid double-wiring), pulls existing strokes for the new member's current hole, and prunes `otherStrokes` + `presence` for departed members.**Lifecycle**: started from `ActiveRoundView.onAppear` (watch) and `HolePlayView.onAppear` (iOS) via `startPlaygroupChannelIfNeeded`, which async-checks `currentOpenPlaygroup()` and only starts if one exists. Stopped on disappear. `updateCurrentHole(_:userId:)` is called whenever `currentHoleIndex` changes so other-player stroke fetches stay scoped to what's actually on screen. The `liveDotsEnabled` toggle controls *publishing* — receivers always see other players regardless. Settings UI: iOS `SettingsView` Multiplayer section + watch `OptionsView` Settings section.

- `MultiplayerView` (shared, in `GolfTracker/Views/Shared/`) - Entry-point UI for multiplayer. Three sections: (1) current playgroup with member list + Leave/End button, (2) pending join requests (host-only) with Accept/Decline per row, (3) Host Round button + nearby joinable groups. iOS reaches it via Settings → Multiplayer (a real NavigationLink — it was an inert grey Label until 2026-07-31, so the iPhone had NO path to host or join at all); watchOS reaches it via Options → Settings → Multiplayer. Member rows show colored dot + display name (looked up via `PlaygroupService.profiles(for:)`). Both Host and nearby-fetch read `LocationManager.shared.location?.coordinate` so the host's row carries coords and joiners only see groups within range. The "Host Round" button is gated on the user having an active round — `currentRoundId` is read from `WatchDataStore.shared.currentRoundId` on watchOS and `DataStore.shared.currentRoundId` on iOS (set by `HolePlayView.onAppear` and cleared on disappear).
- `GolfCourseAPIService` - Shared (iOS + watchOS). Calls the `golfcourse-search` Supabase Edge Function (which proxies GolfCourseAPI so the API key never ships in the app binary) and reads cached scorecard data from `course_tees` + `course_tee_holes`. The Edge Function caches every returned course's tee data server-side as a side effect, so subsequent reads can use the DB cache directly. Used by `RoundResolver.resolveScorecard()` after the user picks a course — searches by course name, picks the best match by location proximity (within 1km), attaches the result as `Resolution.scorecardCourse` for the tee picker UI to consume.

### Tee selection on the watch

After `RoundResolver` returns a `Resolution` with `scorecardCourse != nil`, `WatchDataStore.handleResolved()` loads the cached tees for that course (`GolfCourseAPIService.cachedTees(forExternalCourseId:)`) and presents `pendingTeePicker`. The watch home view binds a sheet to that and shows `TeePickerView` — list of tees sorted by gender (men first) then total yardage descending; each row shows tee name, total yards, par, course/slope rating, gender. User picks a tee → `Round.selectedTeeId` and every `Hole.teeId` in the round get set to that tee. Skipping the picker (or no scorecard data available) starts the round with `selectedTeeId = nil`.
- `RoundResolver` - Shared (iOS + watchOS). Orchestrates the "start a round from here" flow:
    1. **Shared-courses and OSM run in PARALLEL, then merge** — `fetchSharedCoursesNear` (bbox over the `courses` table) alongside `OSMCourseService.fetchCandidates`, deduped by `osm_id` with the shared row winning so its cached polygons survive. MapKit `.golf` POI search is the fallback when OSM returns nothing. There is no separate "Play <name>?" pre-prompt: a known course simply appears in the merged candidate list, and `resolveExistingShared` reuses its cached OSM data instead of re-querying Overpass. (An earlier design did prompt first — `existingCoursePrompt` / `existingCourseProximityMeters` are gone with it.)
    2. Course pick: automatic when the nearest peer is far enough away, `coursePicker` callback otherwise → `OSMCourseService.fetchCourseGeometry` for the picked course's polygon.
    3. Returns a `Resolution { courseId, courseName, osmData, tier }`. Streams status via `progress(Step)`.
    **`docs/ROUND_START_FLOW.md` is the source of truth for this flow** — it carries the full branch matrix (OSM tier × scorecard coverage × cross-user consensus) and is kept in step with the code. This bullet is a summary; when the two disagree, believe that doc and fix this one.
    **Courses: shared and personal** (migration 00055). A course with an `osm_id` is **shared**: every signed-in user reads it and **no client writes its row or supplies its data** (migration 00056). `RoundResolver.registerSharedCourse` sends only the picked OSM element (and the elements it grouped as the same course) to the **`register-osm-course` edge function**, which fetches them itself from the OSM editing API (`api.openstreetmap.org/api/0.6`: the element's `full` call for its tags and outline, a `map` call over the outline's bounding box for its holes, greens, tees, fairways and bunkers; Overpass refuses requests from the Supabase edge with 406), refuses anything that is not a named `leisure=golf_course` (siblings must also be golf courses within 500 m), builds the `OSMCourseData` (`supabase/functions/register-osm-course/osm.ts`, the server twin of `OSMCourseService`'s parsing), and stores it through `register_osm_course` (service role only), which creates the row or, for an `osm_id` already registered, fills in only what it lacks and derives the shared holes. A scorecard id is kept only if `golfcourse-search` has cached it. **The round uses the course id the function returns**, which is the existing course's when another device registered that `osm_id` first; if the function cannot be reached the round plays from this device's own OSM fetch with an unregistered id (`resolveUnregisteredOSM`). A scorecard found later for an existing shared course goes through the same function. **The green detector's results on a shared course are written once** (`store_course_blob_detection`): every device and user picks greens from that set and pick votes compare its blob ids, so a later run gets the stored set back, and `DataStore.uploadBlobDetectionResults` adopts it and resends it to the watch; on the caller's own course a new run replaces the old. Every other course is **personal**: `created_by` defaults to the caller, and only its owner can read, change or delete it. `SupabaseSync.upsertCourse` skips shared courses (`Course.isShared`, which needs the local `osmId`; both stores set it from `Resolution.osmId` at round start). **User-typed course names are private to their author** — user-generated content surfaced to other players nearby would need moderation, reporting and blocking (App Review guideline 1.2) — and that privacy is now the select policy, not only `fetchSharedCoursesNear`'s filter (a row with an `osm_id`, or the caller's own). `courses_rls.sh` asserts these rules. Consequence: a real course that happens to lack an `osm_id` also becomes per-user, which is the safe direction. This is also what makes `userGeneratedContent: false` an honest answer on the App Store age-rating declaration (4+).
    **Manual path — user names the course.** When nothing identifies where the user is (no shared row, no OSM, no MapKit POI) the picker's last entry is `.manual`. Picking it fires the `courseNamePrompt` callback (third UI callback alongside `coursePicker`/`scorecardPicker`, so the resolver stays UI-free), and `insertUserNamedCourse` writes the user's own (personal) `courses` row with their GPS as `center_lat`/`center_lon`, upserting on `id`. **A name is required**; cancelling or submitting blank aborts the round. Reuse needs no extra machinery: `fetchSharedCoursesNear` already matches on `center_lat`/`center_lon` within `nearbyRadiusMeters` (4800m), so the next round there surfaces the course by name in the normal picker. This replaced throwaway `"Unlisted course"` / `"Quick Start"` courses — the old code minted a *new* anonymous course row per visit (5 distinct `Quick Start` courses in 5 taps), none re-recognisable, and `StatsEngine` groups By Course on `courseId` so each rendered as its own identically-titled venue. The watch's variant created **no `Course` row at all** (`Round(courseId: UUID(), …)` pointing at nothing), which is why those rounds orphaned in Supabase. **Nil completion starts nothing** on both platforms — it used to fall back to `startManualQuickRound`, which now prompts and would reopen the prompt the user just cancelled.
    **Tier classification (`OSMCourseData.tier`):** `full` iff hole refs are exactly `{1, 2, ..., N}` — pure integers, no duplicates, contiguous. Bethpage umbrellas (5x dups) and Pinehurst overlap edge cases (1 dup) fall to `partial` and the round starts manual.

### Core Data Models

All data models are defined in `GolfTracker/Models/Models.swift` and are shared between iOS and watchOS targets:

- **Course**: Contains holes, optional rating/slope/city metadata
- **Hole**: Number, coordinates, par (3/4/5)
- **Round**: References a course, contains strokes, targets, completion status, current hole index. Lifecycle: `endedAt: Date?` (nil while in progress; set by manual End Round, the inactivity sweep, the off-course sweep, and the auto-end-prior path when a new round starts) + `lastActivityAt: Date?` (bumped on stroke add and hole-index change — single shared column, either device updating it satisfies the cross-device "both devices inactive" semantic since Realtime sync echoes the value).
- **Stroke**: GPS coordinate, club, timestamp, optional trajectory heading, penalty flag
- **Target**: Hole-specific GPS markers for distance reference
**Important**: When adding new fields to models, ensure they are `Codable` as they're serialized for JSON persistence and WatchConnectivity transfer.

### Motion Detection System

The swing detection system (Watch only) uses CoreMotion at 100Hz. All timing uses `data.timestamp` (CMDeviceMotion sensor time), not wall clock. 15 channels per sample: userAccel XYZ+Mag, rotation XYZ+Mag, gravity XYZ, pitch/roll/yaw.

**Detection Modes** (`SwingDetectionManager.swift`, `DetectionMode` enum):
- `off` — disabled
- `unifDetect` — **current primary mode**: single `UnifiedDetector` with tri-state classification (putt/swing/ambig) and type-aware pairing (in the algorithms package)

**The detector is in the algorithms package.** `UnifiedDetector` (setup, backswing-top and forward-swing-peak event streams, tri-state classification, type-aware pairing), its post-pairing gates (`PostPairingGates`) and swing direction are pure code in `StrokeSaverAlgorithms`; their design, thresholds and Python reference live in that repo's `CLAUDE.md` and `docs/`. `SwingDetectionManager` feeds `MotionSample`s to `UnifiedDetector.process`, picks up `pendingShapeEvent` (a `UnifiedShapeEvent`) and fires `fireSmartDetection()`.

**Every detection carries a per-gate report, passes included** (`swing_events.gate_report`, migration 00049): `{gate: {value, limit, margin, passed}}` for all eight post-pairing gates. `gate_fails` on rejections was the only verdict ever recorded, so a detection that squeaked through carried raw values and nothing else — "did this barely pass, and on which gate" meant fetching the thresholds and doing the arithmetic by hand. **`classification` / `swing_type` now record the detector's verdict.** Both columns had stored `club_type` since the table was created, so no row before build 68 says whether the detector thought it saw a putt or a swing.

**Detector thresholds live in `detector_config`, not in the binary** (migration 00048, `DetectorConfig.swift`). Tuning used to cost a build, an upload, and a wait for the watch to sync — minutes per experiment, for experiments judged in seconds — and it raced the analysis, since what a stroke was measured against was whatever happened to be compiled into that day's build with nothing recording which. The table is key/value so a new parameter needs no migration; a row with `user_id` set overrides the shared `user_id IS NULL` default. `startMonitoring` refreshes before the first sample is judged, covering rounds and Swing Test alike, and a failed fetch leaves whatever is already in force — a dropped connection must never change gate behaviour mid-round. **There are no threshold literals in the app at all.** `DetectorConfig` fetches and caches the table and hands the resolved set to the package with `DetectorParameters.install`; every gate and detector threshold is a computed read through `DetectorParameters.d` / `.i`, so the numbers exist in the table and nowhere else. **An incomplete config is refused at load, never discovered at a read**: thresholds are keyed by the package's `DetectorKey` (every key the code reads), and `DetectorParameters.install` takes a set only when it has every key with a finite value. Anything less is logged as `detectorConfig.rejected` (naming the missing and invalid keys) and the set already in force — the last good fetch, or the disk cache — keeps judging strokes; a rejected set never reaches the cache. Detection is gated on `DetectorParameters.isLoaded`, so a device that has never loaded a complete set does not detect. The set lives behind a lock, since `install` runs on the main actor and the 100 Hz motion queue reads it. The package's `swift test` checks that the seed carries every `DetectorKey`; adding a threshold means a `DetectorKey` case, a seed row and a live row. The baseline rows are seeded from the package repo (`supabase/seed/detector_config.sql`), not from migration 00048. **The preset system (`applyUnifPreset`, `UnifDetectPreset`) and the iOS `MotionParametersView` were deleted**, along with 21 `devParam` write cases: each assigned literals into the gates and so became a second writer racing the table the moment it became authoritative. They solved "change several thresholds without a build", which `tune.py` now does against the table itself. Change a value with the package repo's `swing_detection/tune.py <key> <value>`; it takes effect at the next monitoring start. **Every detection and rejection is stamped with the values it was judged under** (`swing_events.detector_config`, `false_negative_candidates.detector_config`) — without that, tunable thresholds silently destroy the analysis, because rows from either side of a change get pooled and compared as though they meant the same thing.

**Threads.** `processDeviceMotion` runs on `motionQueue` and the 800Hz batches on their own queue (the 800Hz override confirms shapes there too), while monitoring starts and stops on main (`startMonitoring`/`stopMonitoring` are `@MainActor`). Anything two of them touch is locked: background code reads `monitoringActive` (lock-backed), never the `@Published isMonitoring`, which is for the UI; every other `@Published` setting the queues consult (`detectionMode`, `requirePostPairingGates`, `autoAdd`, `selectedClubTypeName`, `testModeActive`) mirrors itself from its `didSet` into `engineState`, which also holds the 800Hz stream flags, and off-main code reads `engine`; the detector is used only through `withDetector` (one lock, never held while a detection fires), and its reset runs on `motionQueue` behind samples already queued (`resetToIdle`); the rejections since the last stroke sit behind `rejectionsLock` (UI reads `pendingRejectionCount`); the latest sample time and the lookback boundary move together under `sensorClock`; stream liveness is `raw800Liveness`; `latestRawAccelTime` is an `OSAllocatedUnfairLock`; the 3-minute 100 Hz `rollingMotionBuffer` is a `TimeWindowBuffer` behind `rollingBufferLock`, read by time window (`elements(from:to:)`). `WorkoutManager` is `@MainActor`: `endWorkout` clears its flags before returning so a start on the next line is not ignored, delegate callbacks from a session already replaced are dropped, and off-main code reads the session state through `WorkoutManager.currentSessionState`. The buffer advances a start index rather than removing from the front of an array, which at 18,000 samples shifted the whole buffer on every sample.

**Two-stage contact gate (unifDetect)**: post-pairing gates are evaluated first on **100Hz device-motion userAccel** (`checkPendingUnifShapesWithDM`), the primary contact path. Shapes that pass fire immediately; shapes that fail are queued for a **800Hz raw-accel override** (`checkPendingUnifShapes`) while the 800Hz stream is running. Both stages call the same `PostPairingGates.evaluate` over the windows `PostPairingGates` defines (`windowEnd`, `baselineStart`, `reversalEnd`), and the verdict is a `PostPairingGateResult`.

- **800Hz must never spin down during an active setup** (`unifSetupActive`). `checkPendingUnifShapes` stops the stream once no shapes remain to check, and had no notion of a setup being in progress — so a shape left over from an EARLIER setup could kill the stream during the CURRENT one, and because `startBatchedAccelForPutt` returns early when already running, the new setup never re-armed it. The user stands over the ball, the sensor switches itself off, and returns after impact. Measured on a missed putt: setup began 18098.80 with the stream up, stream stopped 18100.30 **mid-setup**, contact at 18102.81 had no 800Hz whatsoever, stream resumed 18102.90 — 90 ms after the ball was struck. Arming itself is fast (20 ms measured), so this was never spin-up latency. This is the mechanism behind "soft putts are consistently missed": the contact gate is asked to judge an impact the sensor was switched off for, which reads downstream as `ct_sum=0.000, ct_n=0` — indistinguishable from a stroke too soft to register.

- **The 800Hz slice is re-uploaded after the batches land.** `CMBatchedSensorManager` delivers in ~0.5 s batches (visible as sample counts clustering on multiples of ~400), while `fireSmartDetection` snapshots the ring the instant a shape is confirmed, around `fsPeak + 0.3 s`. The batch carrying impact has usually not arrived, so the stored slice stops **before** the forward-swing peak — measured across nine detections, seven ended early, by 0.08 s to 2.45 s. Downstream that is indistinguishable from a stroke with no contact signal, and it is what produced `ct_sum=0.000, ct_n=0` on candidate after candidate: not a putt too soft to measure, a recording that stopped before the thing being measured. `fireSmartDetection` now re-slices after `rawAccelSettleDelay` (2.5 s) and re-uploads via `uploadRawAccelLate` (`upsert: true`, path derived from the event id so no DB column changes); `SwingTestSession.captureLookback` defers its upload the same way, counting and confirming to the user immediately. **Detection timing is untouched** — only the stored copy is corrected, so the watch still behaves exactly as it does in a round.

**Swing Test Mode does NOT special-case 800Hz gating, and the 800Hz ring is sized to the lookback window.** Running it continuously in test mode was tried and reverted within the hour: the mode exists to reproduce what a round does, and a stream that is always on cannot reproduce one that spins up too late, so the very bug being hunted would have been hidden. Separately, `eventBufferDuration` was **5 s** while `lookbackMaxSeconds` is 15 — so a Missed It could only ever recover the last third of its own window. A putt more than ~5 s before the button press had its 800Hz already rolled out of the ring while the 100 Hz motion (180 s) survived intact, which is how one capture came back with three setups and no contact data at all; measured fragments were 0.5-2.5 s against a contact gate spanning ~0.6-1.0 s, so the short end did not cover the stroke. Both now derive from `SwingDetectionManager.lookbackMaxSeconds` so they cannot drift apart. Retention costs memory (~480 KB), not battery — the drain is running the sensor, not keeping its output.

**800Hz capture is armed by `startMonitoring`, not by picking a club.** `rawAccelRunningForCapture` gates both starting the `CMBatchedSensorManager` hardware and whether delivered samples are written to `eventRawAccelBuffer`, and it is set only inside `updateRawAccelForCapture()`. That function used to be reachable from exactly two `didSet`s — `detectionMode` (which fires at init only when its UserDefaults key already exists) and `selectedClubTypeName`. Rounds therefore worked **by side effect**: selecting a club armed the buffer. Anything that monitored without a club change captured nothing, silently — Swing Test Mode selects no club, and its first session uploaded 11 events every one of which carried `rawAccelSampleCount=0`, so the contact evidence soft putts most depend on was simply absent with no error logged anywhere. `startMonitoring` now calls it directly, since monitoring starting is the actual precondition. **Do not re-couple capture arming to club selection.** The club decides nothing about capture at all. A test session's `club_type` stays null rather than being defaulted, because a wrong club label is worse than a missing one.

**Raw Accelerometer (800Hz) — on for the whole session**: `CMBatchedSensorManager` batches raw accel at 800Hz and needs an `HKWorkoutSession` in `.running`. In `.unifDetect` it runs whenever monitoring is on (`shouldRunRawAccelHardware`) — started by `startMonitoring` or the workout's `onSessionRunning`, stopped by `stopMonitoring`, rounds and Swing Test alike. It used to be armed per setup and spun down by a 3s setup-end `Timer`, but that Timer was scheduled from `motionQueue` (an OperationQueue, no run loop) and never fired, so gating saved about a third of stream time at most, and its arm/disarm cycle left a stream that died while armed with no way back (2026-08-31: 35 minutes with no vibration data). **Do not reintroduce per-setup gating without fixing that scheduling and measuring the battery difference first.** Start/stop are serialized by `rawAccelControlLock`. `checkRaw800Liveness` (1Hz from the motion tick) measures silence from the last batch or the last (re)start, logs `rawAccel.stream.down` past 2s, and restarts the stream via `restartRawAccel` (`rawAccel.stream.restart`) with backoff doubling from 2s to 60s. The `detector_config` row `setupEndTimeoutS` is inert — nothing reads it.

**Swing direction (ball launch bearing)**: `UnifiedDetector.swingBearing(bsTopT:fsPeakT:)` (package) returns the launch bearing in degrees clockwise from north for a paired shape, or nil; `fireSmartDetection` writes it to `DetectedSwing.trajectoryHeading`. The detector's own pairing is the segmentation, so there is no separate phase-detection step. Requires `.xMagneticNorthZVertical` attitude, and `MotionSample` carries yaw plus full gravity and user-acceleration vectors for it. **Headings are never fabricated**: the bearing-to-hole fallbacks in `recordStroke`/`recordStrokeFromMotion`/`addLastSwingAsStroke` and iOS `captureAimDirection`'s "bearing-to-hole + 45°" were all removed — `Stroke.trajectoryHeading` is now swing-derived or nil. Those fallbacks are why the old "Avg Shot Deviation" stat measured 0.049° across 102 tee shots (it compared bearing-to-hole against bearing-to-hole); that stat is deleted. Historical Supabase rows still hold fabricated headings — exclude strokes before 2026-07-30 from any `trajectory_heading` analysis.

**Watch-requested blob runs only happen with the iPhone app on screen.** WatchConnectivity launches the phone app in the background to deliver the watch's request, and the analyzer's MapKit snapshots do not complete there — the 2026-09-07 Blue Sky run started that way and died with nothing logged. So `DataStore` puts every watch request in `watchHoleDetectionQueue` (UserDefaults, survives a kill) and `drainWatchHoleDetectionQueue` runs it only when `applicationState == .active`, otherwise telling the watch `queued`; the scene-phase `.active` hook drains it. Every run ends in `finishHoleDetection`, which reports `done`/`failed` over `sendHoleDetectionStatus`, dequeues, and ends the `beginBackgroundTask` that covers a run the user backgrounds midway. The analyzer centers on placed holes, then the course's stored `centerLat`/`centerLon`, and only then the phone's GPS — a queued run can execute hours later somewhere else. Watch side: `requestBlobsFromPhone` + `BlobRequestCard` (see `docs/ROUND_START_FLOW.md` Stage 4).

**Hole detection (blob analyzer)**: `HoleDetectionAnalyzer` (`HoleDetectionAnalyzer.swift`, iOS) renders Apple Maps *standard* tiles via `MKMapSnapshotter` (forced light mode + 1× scale so the fill colour is stable) and flood-fills on Apple's exact golf-green fill `RGB(186,232,153)`, scoring candidates with nearby sand `RGB(245,242,218)`. It is the fallback for green geometry — `needsBlobDetection = (osmData == nil) OR (tier != .full) OR (greens < holes)` — and it's load-bearing: measured OSM green coverage is zero at 3 of the 8 courses played and partial at 2 more. **Tiles run concurrently** (`maxConcurrentTiles`, 9); they're independent and the old sequential loop was the entire ~13s run (measured from `client_events`, n=6, 11-14s). `snapshotStandardMap` retries on `MKError.loadingThrottled` with backoff, a failed tile no longer sinks the run (partial coverage still places most greens), and results merge in tile order so output is deterministic. `tilePixelSize` is 1024 (1.95 m/px, ~10 px across a green) rather than 1600 — 9.4M pixels per run instead of 23.0M, and ~75MB peak with all 9 in flight instead of ~184MB, which is what makes 9-wide safe. Tiles whose bounding box misses every `boundingPolygons` outline are skipped: blobs outside those polygons are *already* dropped by the output gate, so such tiles only ever produced rejects — no extra trust in OSM required. (Currently inert: `boundingPolygons` is null on all existing course rows, which predate it, and `resolveExistingShared` reuses the cached row.) **Thresholds are declared in physical units** (`minimumBlobAreaSquareMeters`, `sandScanRadiusMeters`) and converted via `metersPerPixel` — as bare pixel counts they silently re-tuned when `tilePixelSize` changed (20 px meant 31 m² at 1600 px but 76 m² at 1024 px). Cost is **once per device per course**, not per round: `startHoleDetection` checks the local disk cache first; `courses.blob_detection_results` only saves a *different* device the run.

**Data collection / motion capture**: the standalone data-collection mode and motion-capture pipeline (`SwingDetectionManager+DataCollection.swift`, `SwingDetectionManager+MotionCapture.swift`, `AccelTestView`) were removed in fdc662f. Swing-event motion slices now upload to Supabase via `SupabaseUploader` (false-positive slices included, sent when a detected stroke is undone).

- **`swing_events.label` is about the DETECTOR, never the scorecard.** It answers only "was this correctly identified as a golf swing?" Whether it counted as a stroke is a separate axis, `not_a_stroke_reason` (migration 00047). A **practice swing is a correct detection** — real swing motion, correctly identified, just not a shot — so the practice-replacement path in `autoAddStrokeFromSwing` calls `markPracticeSwing` (`positive/high` + `reason='practice'`), not `markFalsePositive`. It used to call the latter, the same as undo, which trained the model against its own correct answers; and because `shouldReplacePreviousStroke` fires only when the user swung twice in one spot without walking, those were the most unambiguous positive samples the app produced. Pre-00047 `false_positive` rows are therefore a **blend of genuine misfires and mislabeled practice swings**, and `swing_events` alone cannot split them — the row records `created_at` (detection time), never when the label was flipped. They *are* separable by joining `client_events` on `swing.update.falsePositive.ok` (carries event id + `occurred_at`): a practice replacement flips at the instant the next detection is created, an undo flips seconds-to-minutes later with nothing beside it. Also, a practice replacement is never a putt, so every putt marked `false_positive` is a genuine undo. That join only reaches sessions with logging on before 2026-08-23, which is why nothing backfills it. `positive/low` stays deliberately weak: the detector fired and the user didn't object, which includes detections nobody noticed.

- **False negatives need TWO capture paths, because there are two kinds of miss.** `recordRejection` is reachable only from the post-pairing gates, so `false_negative_groups`/`candidates` (`capture_reason='rejected_shapes'`, built from `claimAllRejectionsSinceLastStroke` on a manual stroke add) can only describe a miss where setup, BS-top and FS-peak all paired and a contact gate then killed it — it records *which* gate via `gate_fails`. A swing failing earlier (no setup event, no valley/peak clearing prominence, pairing blocked by an intervening event) produces no rejection at all, so the buffer is empty and `uploadFalseNegativeGroup` early-returns: **the miss hardest to reconstruct afterwards was the one generating no data.** `capture_reason='lookback'` closes it — the "Missed It" button dumps the raw rolling buffer (`rollingBufferDuration` already retains 180 s of 100 Hz motion, so nothing new has to be recorded). The window ends now and starts at the later of *now − 15 s* and `lastCaptureBoundarySensorTime`, which advances on every fired detection (`markCaptureBoundary`) and every capture — so it shrinks to cover only unclaimed ground, and pressing twice sends nothing the second time. Rejections inside the window ride along as candidates for free; **a candidate count of zero is the finding, not a failure** — it means nothing paired.

- **Swing Test Mode** (`SwingTestSession` + `SwingTestView`, watch; iPhone Settings → Developer → "Swing test mode (watch)", mirrored via the standard `devParams` path). Runs the detector exactly as round play does but starts no round. Detections are ordinary `swing_events` stamped with `test_session_id` so they feed the same training set and stay filterable; `swing_test_sessions` stores the counters the watch displayed so a session can be audited without assuming every upload landed. Optional **club** (→ `club_type`, null when unselected) and optional persistent **note** (`swing_test_notes` + `swing_test_note_events`, migration 00050 — linked to every event saved while active, kept off `swing_events` because round swings never carry one). **Farm FP** (`farmFalsePositives`, persisted) flips every detection to `false_positive/high` as its id lands, with no press — for sessions where a swing is impossible (driving, eating, carrying the clubs) so every detection is a misfire by construction; the flip is stamped `farmed: true` in the log, since a blanket claim about a session is weaker evidence than a person rejecting one detection. Two non-obvious requirements: **`autoAdd` is forced on** for the session (manual mode holds the event pending for a popup that doesn't exist here and never publishes the event id the False Positive button needs), and **the GPS precondition in `fireSmartDetection` had to go** — it used to `guard let location` and return, discarding the detection *and* its motion slice, so every test detection indoors would have vanished at that line. Position is context for a stroke, not a precondition for detecting a swing; test detections carry `kCLLocationCoordinate2DInvalid` rather than a plausible-looking zero. In a round the guard still applies, which means a swing before the first fix is dropped — a real false-negative source.

**Tee hold — full GPS from green to first stroke.** `LocationManager.beginTeeHold()` (called from `handleCurrentHoleChange`) coerces `.full` until `releaseTeeHoldIfNeeded()` fires on the hole's first stroke (`WatchDataStore.addStroke`). Without it the distance heuristic alone leaves a hole in the height map: it runs `.full` inside `gpsModerateYards` (200 yd) of the pin, so the green and approach are covered, but at the tee of a par 4/5 you're beyond that — so the walk from the previous green, the tee box, and the tee shot all record at `.moderate`, which requests 10 m accuracy, and `ElevationFoldIn.accuracyFactor` **excludes anything ≥10 m outright**. That stretch burned GPS and was then discarded. Measured across the existing readings: median accuracy **7.4 m**, only **18%** at the ≤5 m full-weight mark, **34% dropped entirely**. The green and the tee are the hole's two elevation anchors; the fairway between them interpolates.

**GPS Power Modes (iOS/watchOS)**: `LocationManager.setGPSPowerMode` toggles `.full` (1m accuracy, 1m filter) and `.moderate` (10m / 10m). `ActiveRoundView.updateGPSForDistance()` drops to `.moderate` beyond `gpsModerateYards` (default 200 yd). **Selecting the putter forces `.full`** — the green is the densest cross-round overlap on the hole, i.e. the elevation pipeline's per-hole sync point (this used to force `.moderate`; flipped 2026-06-12). The radio is never fully stopped during a round because AutoAdvance needs GPS updates to detect walking off the green to the next tee. **First-tee sync hold**: `startPathRecording` coerces `.full` until the elevation calibration's first offset solve, the round's first hole being played through, or the hole having no history to sync against (all released by `ElevationReadout`, no time cap) — the first tee has no prior-green sync to lean on; later holes re-sync at each green. **Accuracy weighting**: every `PathSample` captures `horizontalAccuracyMeters` (uploaded as `round_altitude_readings.h_acc`, migration 00041); elevation calibration/fold-in weight samples by `ElevationFoldIn.accuracyFactor` — full weight ≤5 m, taper to zero at 10 m, excluded beyond, legacy nil rows at 0.5. **Battery telemetry**: `ClientEventLogger.logBattery` logs battery % on every hole change — on the watch, every write of the round's hole index, including `addNextHole` and `addHole`, which skipped it until build 71 so a round whose holes were all added in play (Blue Sky, 2026-09-07) recorded none (both platforms, ALWAYS on — it passes `force: true` to bypass the logger toggle, added after the 2026-07-05 dead-watch round had zero battery data to audit) so GPS-fidelity policy can be decided from per-hole burn data.

## Algorithms package

Swing detection, swing direction and the elevation solver are not in this repo. They are in
`JJGantt/StrokeSaver-Algorithms` (private), checked out as the `StrokeSaverAlgorithms/` submodule.
That repo has its own `CLAUDE.md`, which is where their design, thresholds and history are written.

**The boundary is pure algorithm code.** Everything that talks to CoreMotion, HealthKit, Supabase,
the UI or the round stays here; the package takes plain values and returns plain values. The watch
target (only) links the package's `StrokeSaverAlgorithms` library, and every file that calls it says
`import StrokeSaverAlgorithms`. The interface the app uses:

| Package API | Called from |
|---|---|
| `UnifiedDetector` (`process(_:)`, `pendingShapeEvent`, `buildResult(from:)`, `reset()`, `log`) | `SwingDetectionManager` |
| `UnifiedDetector.swingBearing(bsTopT:fsPeakT:)`: launch bearing for a paired shape | `SwingDetectionManager.fireSmartDetection` |
| `MotionSample`, `UnifiedShapeEvent`, `SwingDetectionResult`, `SwingType`, `StrokeClassification` | detection, upload and stroke paths |
| `PostPairingGates.evaluate(...)` → `PostPairingGateResult`; `windowEnd` / `baselineStart` / `reversalEnd` | `SwingDetectionManager+PostPairingGates` |
| `DetectorParameters.install(_:)` → `InstallResult`, `.isLoaded`, `DetectorKey` | `DetectorConfig`, `SwingDetectionManager.processDeviceMotion` |
| `AlgorithmLog.diagnosticSink`: the detector's diagnostic events, forwarded to `ClientEventLogger` at `.diagnostic` | installed in `SwingDetectionManager.unifiedDetector` |
| `resolve-hole-heights` edge function (HTTP, not Swift) | `ElevationFoldIn.requestGlobalResolve` |

**Changing an algorithm** is a commit in the submodule, pushed to its own repo, followed by a commit
here that moves the submodule pointer (`git add StrokeSaverAlgorithms`). A build always uses
whatever commit the pointer names, so an unpushed submodule commit builds on this Mac and nowhere else.

**The edge function is deployed from the package repo**, not from here: `supabase/functions/` in
this repo holds `course-height-field`, `golfcourse-search`, `register-osm-course` and
`delete-my-data` (`supabase functions deploy <name> --project-ref oumnicnvayqrbfbljgyl`). Deploying
from here never touches `resolve-hole-heights`.

**Migrations stay here, seed data does not.** `supabase/migrations/` is the whole schema and
`supabase db push` from this repo is still the only way it changes. The baseline `detector_config`
rows that 00048 used to insert are in the package repo (`supabase/seed/detector_config.sql`), and the
one-off data statements in 00008, 00009 and 00038 (which named the sole user's id) were removed from
those files; the originals are kept in the package repo. All of those migrations were already
applied, and the CLI tracks applied migrations by version, so editing them changes nothing on the
live project. A fresh project gets the schema from here and its detector thresholds from the seed.

## Key Implementation Patterns

### Distance Calculations

All distance and bearing calculations use the helper functions in `GolfTracker/Helpers/MapCalculations.swift`:
- `distance(from:to:)` - Returns distance in meters
- `bearing(from:to:)` - Returns bearing in degrees (0-360)
- Formatted output converts meters to yards for display

### Map Camera Behavior

Both live play maps aim from the hole's tee to the pin: the phone's `HolePlayView.updateMapPosition` and the watch's default full view (`ActiveRoundView.updateMapPosition`).
- Pin at the top, the start point at the bottom, rotated along the start → pin bearing
- Start point: the first point of the course map's centerline for the hole (full-tier OSM coverage only), else the hole's first stroke, else the user
- The watch re-anchors whenever the hole's first remaining stroke changes (deleted, moved, or the last one removed, which falls back to the user), not only on the next GPS fix — `.onChange` on its coordinates in `ActiveRoundView`.
- The frame is fixed for the hole and does not follow the user, so the shots already hit, their distances, the shot line and the trail stay in view. Framing from the user (the phone did until 2026-09-14) put every earlier shot below the bottom edge.

This is implemented using `MapCameraPosition.camera()` with computed center point, bearing, and distance. The phone zooms to 4.4× the start → pin distance, which keeps the start's shot marker clear of the hole panel and the pin clear of the yardage header.

**A hole's strokes are read in stroke order on both maps.** Each marker's yardage (a shot's distance to the next one; for the latest shot, its live distance to the user) and its elevation delta are computed from the *next* stroke by position, and `Round.strokes` is a SwiftData relationship with no order — unsorted, hole 14's drive was labelled 379 (tee to user) and the layup 250 (the drive's distance). The watch's marker lists in `ActiveRoundView` already sorted by `strokeNumber`; `HoleMapView` now does too.

### Stroke Recording Flow

When recording a stroke (on either iPhone or Watch):
1. Capture current GPS location
2. Get current hole from active round
3. Create Stroke object with auto-incremented stroke number
4. Calculate distance to hole at stroke moment
5. Add stroke to round's stroke array
6. Sync stroke to other device via WatchConnectivity
7. Save to persistent storage (JSON)

**Important**: Stroke numbers are auto-incremented per hole. When adding strokes, always filter existing strokes by current hole number to get the next stroke number.

### Hole Navigation Synchronization

The `currentHoleIndex` field in Round is synchronized bidirectionally, **through
Supabase, not WatchConnectivity**: the writing device upserts the round, and the
other device picks it up via `RealtimeSync`'s `rounds` postgres-changes stream (with
`reconcileRoundsWithSupabase()` as the catch-up path, since postgres-changes don't
replay across a dropped socket).

So a hole-navigation change needs a targeted `SupabaseSync` write at the mutation
site (`updateCurrentHole`) — nothing else will sync it. There is no `WatchConnectivityManager.sendRound()`;
round and stroke sync left WatchConnectivity when Supabase became the source of
truth, and the method was removed with it.

## Common Workflows

### Adding a New Club Type

Club types are `ClubTypeData` rows (SwiftData + Supabase `club_types`), not an enum. The
16 built-ins are declared in `ClubTypeData.defaultClubTypes()`; users can also create
their own via `AddClubTypeView`.

1. Add the type to `ClubTypeData.defaultClubTypes()` **in bag position** — that array's
   order IS the canonical display order (see below).
2. Nothing else. Every list site inherits the new type and its position automatically.

**Bag order is user-owned and persisted.** `ClubTypeData.sortOrder: Int?` (SwiftData +
Supabase `club_types.sort_order`, migration 00042) is the authoritative 0-based position.
The drag-to-reorder in `ClubSetEditorView` (`.onMove` → `DataStore.moveClubType`) renumbers
every type and pushes the result up. Custom types get a real position this way, which is
the whole reason the order is stored rather than computed.

Ordering helpers live in `Models.swift`: `[ClubTypeData].inBagOrder()` sorts by `sortOrder`
when set, `.renumberBagOrder()` stamps positions from array order, and
`ClubTypeData.defaultBagOrderIndex` supplies the fallback for anything never arranged.
`canonicalOrder` is derived from `defaultClubTypes()` so there's a single declaration and
no parallel list to drift; `defaultClubTypes()` self-stamps `sortOrder` from array position,
so a fresh install is ordered from first launch.

Ordering is applied **at the load sites** — `DataStore.loadClubTypes()` (iOS) and
`WatchDataStore.refreshClubsCache()` (watch) — so `store.clubTypes` is always ordered and
no consumer needs its own sort. Do not re-sort downstream; delete any local sort you find.
`loadClubTypes` also backfills: types with a nil `sortOrder` land in canonical position,
get stamped, and are pushed to Supabase once. Nil is transient, never a steady state.

Two traps this replaced:
- **Sorting by `averageDistance`** (the previous watch-only fix) breaks for user-created
  types, which have no distance and sort to the bottom, and reshuffles the whole bag
  whenever a distance is edited. Types whose name isn't canonical (user-created, or a
  renamed built-in) are instead slotted by distance against the canonical ladder so they
  land between their neighbors; neither-name-nor-distance sorts last.
- **`moveClubType` used to reorder the in-memory array only.** The drag appeared to work
  and the arrangement evaporated on the next SwiftData fetch, because nothing persisted it.
- iOS never sorted at all, so `StatsView` and the club-set editor rendered SwiftData's raw
  insertion order (`4-Hyb → 5-Wood → 5-Hyb → Pitch → 6-Iron → … → Drive → …`).

### Adding a New Stroke Attribute

1. Add the property to `Stroke` in `Models.swift` (optional, or with a default, so SwiftData migrates existing stores)
2. Add the column in a migration
3. Write it in `SupabaseSync.upsertStroke` and read it in `RealtimeSync.applyStroke` — the row is mapped by hand in each, so a field missing from either never reaches the other device
4. Set it where strokes are created (`DataStore.addStroke`, `WatchDataStore.addStroke`) and show it in `StrokeDetailsView.swift` if it is user-visible

**Note**: Stroke numbering is centralized in `Stroke.nextStrokeNumber(in:holeNumber:)` in `Models.swift` — both iOS `DataStore.addStroke` and watchOS `WatchDataStore.addStroke` call this helper to avoid drift.

### Modifying WatchConnectivity Messages

**WatchConnectivity is not a source of round data** — the server is. The one way
round data travels over WC is the phone forwarding rows it just received from the
server to the watch (`relayRow`, below). Otherwise WC carries: auth-session push
(iPhone → Watch), hole-detection data and requests, dev params / debug-logging
flags, GPS test mode, and motion CSV file transfers. `sendRound` and `sendStrokes`
do not exist.

1. Add the sender to `WatchConnectivityManager.swift` alongside the existing
   `sendAuthSession` / `sendHoleDetectionData` / `sendDevParam` methods
2. Update the receiving callback in `DataStore.setupWatchConnectivity()` (iOS) or
   `WatchDataStore.setupConnectivity()` (Watch)
3. For a dev parameter specifically, no receiver work is needed — the generic
   `devParam` path already writes every key to UserDefaults; add a `case` in
   `applyDevParamToLiveObjects` only if a live `@Published` value backs it
4. Test both directions, and remember `sendMessage` requires reachability while
   `applicationContext` coalesces and survives a gap
5. A context key's receiver must be safe to run repeatedly. The context holds
   every key the sender has ever set, so a write to any key re-delivers all of
   them, and `handleApplicationContext` runs again at every activation on
   `receivedApplicationContext` (a context that landed while the app was closed
   does not reliably fire the delegate). A handler with side effects has to
   recognise a value it already applied: `holeDetectionRequest` by its `at`,
   `authSession` by `WatchAuthSession.receiveFromPhone`'s fingerprint,
   `devParams` by comparing against UserDefaults
6. Context writes made before activation are held in `pendingContextEntries`
   and flushed at activation. Before that, `updateApplicationContext` throws,
   and `AuthManager.init` pushes the login exactly then

## Development Notes

### Data Persistence

Both apps persist via SwiftData (`@Model` classes in `Models.swift`, shared `ModelContext` per platform — see the Data Synchronization section). Supabase is the cross-device source of truth: local writes mirror up through `SupabaseSync`, and changes fan out to the other device through Realtime (`RealtimeSync`).

**Targeted sync at mutation sites.** `DataStore.saveRounds()`/`saveCourses()` persist locally ONLY. Every mutation site owns its own targeted `SupabaseSync` upsert/delete for exactly the rows it changed (the old blanket re-upsert of every round/stroke/target on each save fanned out into hundreds of HTTP requests per recorded stroke). When adding a new mutation path, add its targeted write alongside — nothing else will sync it. Write only what changed: `upsertRound` is the round row alone, a round's holes go through `upsertRoundHoles`/`upsertRoundHole`, and a hole change is `updateCurrentHole`.

**SwiftData relationship arrays are unordered.** Never index `course.holes` / `round.holes` positionally without sorting by `number` first (`WatchDataStore.currentHole` and `HolePlayView.holesSorted` are the canonical patterns). The same applies to renumbering loops.

### Coordinate System Notes

- All coordinates use `CLLocationCoordinate2D` (latitude/longitude in degrees)
- Distances are calculated in meters, displayed in yards (multiply by 1.09361)
- Bearings are in degrees clockwise from true north (0-360)
- `Stroke.trajectoryHeading` is the swing-derived launch bearing (`swing_direction/ALGORITHM.md`), or nil — never the compass
- The compass runs only while a view holds `LocationManager.beginCompass()` (today: the watch green-placement screen); it publishes on `LocationManager.compass`, not `heading`, so a tick doesn't re-render `ActiveRoundView`

### Adding New Holes During Round

Both iPhone and Watch support adding holes during an active round:
- New hole defaults to current GPS location
- Par defaults to 4 (user can select 3/4/5)
- Hole is added to both the Course (persistent) and current Round (active)
- Changes sync immediately to paired device

This is important for courses that haven't been pre-mapped.

## Watch dev install gotcha — "Could not install at this time"
Applies to any dev-signed watch app, StrokeSaver included. Root cause: **Developer Mode on the watch is hidden until the system sees a dev-signed install attempt arrive via the direct Mac→Watch CoreDevice channel.** The iPhone→Watch app-relay path silently fails when Dev Mode is off — surfaces as an IDS socket timeout in `appconduitd` logs and a generic "Could not install at this time" dialog. App Store watch apps install fine because they don't need Dev Mode.

Fix:
1. Verify Mac sees the watch: `xcrun devicectl list devices`. If missing, kick remotepairingd:
   ```
   kill -9 $(launchctl list | awk '$3=="com.apple.CoreDevice.remotepairingd"{print $1}')
   ```
2. Run a direct install to the watch UDID — fails with `Developer Mode is disabled`, but unhides the toggle:
   ```
   xcrun devicectl device install app --device <Watch UDID> .../Debug-watchos/GolfTrackerWatch.app
   ```
3. Watch: Settings → Privacy & Security → Developer Mode → ON. Watch restarts.
4. Re-run the install. Works going forward via either path.
